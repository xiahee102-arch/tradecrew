# 外贸助手：部署与接入

这是一份可运行的 React + Vite / Cloudflare Worker 全栈工程，托管站点使用 D1 持久化业务记录和 R2 存储原始文件及加密渠道令牌。生产数据初始为空，不植入客户、订单、收入或测试订阅。

## 本地工程

```bash
npm ci --cache /workspace/work/npm-cache
npm run build
npm test
npm run db:local
npm run dev
```

本地直接请求 `/api` 默认返回 401，因为认证依赖托管边界提供的 `oai-authenticated-user-id`。集成测试直接在 Miniflare 内注入测试身份，不在应用中提供绕过登录的后门。本地联调请使用受信任开发代理注入测试身份，不能将此代理部署到公网。生产必须由 Sites 身份网关提供且清洗认证头。

主站已配置逻辑 DB/BUCKET 绑定，生产发布工具已完成 drizzle 初始迁移并核对全部11张业务表。主站提供受同一私有访问策略保护的 `/downloads/source.zip`、`/downloads/setup.md`、`/downloads/competition.md` 和 `/downloads/verification.md`。源码包来自构建时的 Git HEAD，不含本地环境密钥、node_modules、Git凭据或生产数据。

生产构建入口 `dist/server/index.js`，内嵌所有编译后的静态资源，`.openai/hosting.json` 指定 D1 / R2。SQL 位于 `drizzle/`；在生产托管迁移前必须确认工具是否自动执行，不能在每次请求中建表。

### MiMo

服务端端点固定为 `https://api.xiaomimimo.com/v1/chat/completions`，`api-key` 头；全部岗位默认统一使用 `mimo-v2.6-pro`（可用 `MIMO_PRO_MODEL` 配置）。在站点运行环境秘密设置中输入 MIMO_API_KEY，不能把密钥发进聊天或写入前端。字段与模型名须以你们比赛账户的实际 MiMo 文档再做一次真实调用核验。

接入步骤：

1. 从比赛主办方或小米 MiMo 开放平台获取 API Key（仅自己保存）。
2. 本地开发：写入项目根目录 `.dev.vars`（已被 .gitignore 忽略）的 `MIMO_API_KEY=`，`wrangler dev` 启动即生效；冒烟脚本也读取该文件。
3. 生产部署：`wrangler secret put MIMO_API_KEY`，或在托管站点的秘密设置中填写。
4. 核验：`node scripts/check-mimo.mjs`。脚本会列出账户可见模型、对 flash/pro 各做一次真实最小调用，并报告该账户接受 `max_completion_tokens` 还是 `max_tokens`。全部 PASS 后再演示。模型名以核验结果为准，若账户模型名不同，同步修改 `MIMO_FLASH_MODEL` / `MIMO_PRO_MODEL`。

程序按供应商返回的实际 input/output token 记录成本，使用上传文档的费率进行保守估算，不计缓存优惠。比赛期免费开放全部岗位，免费预算为 ¥15 / 租户每月（订阅套餐可提升至 ¥30 / ¥120）；目前并发调用没有预扣额度锁，极端并发可能短暂超额，生产扩量前需增加原子预算预留。80% 用量预警、到期前3天提醒和3分钟首回超时提示已接入首页。达到预算时保留首回及其法务审查的 SLA 例外，其余工单暂停。

### Meta 渠道

1. 在 Meta for Developers 创建企业应用，启用 WhatsApp / Messenger。
2. 在主站运行秘密设置中配置 META_APP_SECRET、META_VERIFY_TOKEN 和随机高熵 TOKEN_ENCRYPTION_KEY。
3. 用户在“渠道”输入自己的号码 ID / 主页 ID 和相应访问令牌。主站向 Graph API 核验后，使用 AES-GCM 加密令牌到 R2，DB 仅留 token_ref。不要直接改密钥，否则旧令牌无法解密；轮换需重授权或迁移。
4. 部署 `gateway/index.js` 到可被 Meta 访问的独立 Cloudflare Worker。主站保持私有，不能为了接收回调盲目公开工厂数据。
5. 网关配置 SITE_ORIGIN（主站 origin）、仅对该主站有效的 SITE_BYPASS_TOKEN（由 Sites 平台生成的服务访问凭据）、SCHEDULER_SECRET。凭据不能进入源码。主站也配置同一个 SCHEDULER_SECRET。
6. Meta 配置公共网关 `/webhooks/meta`，订阅 messages、message_deliveries、message_reads；WhatsApp 订阅 messages（含回执）。验证令牌为 META_VERIFY_TOKEN。主站验签，原始事件先持久化再返回 200，随后处理去重和队列；签名失败拒绝。
7. 开发模式使用已接受邀请的 Meta 测试员；WhatsApp 测试号使用事先登记的收件人。验证“手机发消息 → 主站收到 → 买家手机收到首回 → 老板批准报价 → 手机收到报价”。没有手机往返证据时不能标为已完成集成验收。

外部 POST 只经过公开网关的固定三条路径，不能代理任意 `/api`。主站的 Webhook 仍独立验证原服务签名。私有站点服务凭据不能代替用户身份，也不能在业务 API 中访问用户数据。

出站消息采用 CAS 抢占和发送记录。成功后不重复发送；出现超时/网络中断等不确定结果时标为 uncertain 并升级，禁止盲目重试。Meta Send API 不提供通用幂等键，因此不能承诺网络故障下绝对 exactly-once。明确 429/5xx 等可重试错误按退避进入队列；号码无效/权限/过期/退订进入阻塞。现版本需要人工核对 uncertain，不提供一键强行重发。

### 询盘邮件（Resend）

1. 在 Resend 验证企业发送域名，配置 SPF/DKIM，启用 Receiving 并将询盘地址的 MX/路由指向其入站服务；DMARC 策略由域名管理员确认。
2. 在 Resend 创建 `email.received` Webhook，获得 `whsec_` 密钥。先创建占位回调，连接工厂后更新成下述专属路径。
3. 在“渠道 → 询盘邮箱”填询盘地址、API Key、Webhook 签名密钥。服务端验证该地址所属域名在 Resend 已 verified，随后把两个凭据 AES-GCM 加密到 R2。
4. 主站生成 `/webhooks/email?account=<channel-uuid>`，将其放到公共网关域名下，更新 Resend Webhook URL。网关透传 svix-id、svix-timestamp、svix-signature，主站验签、时间窗检查和事件去重。
5. 后台用接收邮件 API 获取纯文本，在原 Message-ID 线程回复；`Auto-Submitted: auto-replied` 避免循环。只允许已有来信线程，已退订不发，不发营销群邮。
6. 现场发一封真实询盘并确认原邮箱收到回复。没有这一步证据时，只能称“适配已实现，待真实联调”。

### 无人值守调度

网关示例 `wrangler.example.jsonc` 含每 2 分钟 Cron。网关 scheduled 对主站 `/api/scheduler` 发送 HMAC 签名请求。配置完成并验证后，将主站 SCHEDULER_ENABLED=true。主站按上海时间每天 09:00 后生成日简报，周一为周报，周一/三/五 10:00 后生成内容草稿；每租户/日期/任务唯一键去重。订阅已过期不运行。队列失败最多 3 次，之后升级至老板；不会越过产品事实、价格或商业承诺的审批关口。

### 支付接口契约

主站：PAYMENT_BRIDGE_URL（你们部署的商户下单 HTTPS 接口）、PAYMENT_BRIDGE_SECRET、PAYMENT_NOTIFY_URL（公共网关 `/webhooks/payment`）。

主站向商户网关发 POST JSON：

```json
{"out_trade_no":"uuid","amount_fen":9900,"currency":"CNY","plan_code":"trial","method":"wechat","description":"外贸助手 试用版","notify_url":"https://public-gateway/webhooks/payment","return_url":"https://main-site/#account","expires_at":"ISO8601"}
```

请求头 `X-Trade-Timestamp` 为毫秒时间戳，`X-Trade-Signature` 为 `HMAC-SHA256(secret, timestamp + '.' + raw_json)` 十六进制。商户网关必须验签与时间窗（5 分钟），金额不能采用前端输入。网关调用微信 Native/支付宝当面付，返回 `{"checkout_url":"https://your-pay-gateway/checkout/order"}`。checkout_url 是展示原生二维码或跳转官方收银台的你方安全收银页。

微信回调必须先由商户网关使用微信平台证书验证 RSA 签名并解密资源，支付宝回调用支付宝公钥验证 RSA2；核对商户号/应用 ID、金额、币种、交易状态、订单号，并通过渠道查询补偿不确定状态。之后向主站 notify_url 转发重新签名的统一事件：

```json
{"out_trade_no":"uuid","amount_fen":9900,"currency":"CNY","method":"wechat","status":"paid","transaction_id":"provider-receipt"}
```

主站不把统一 HMAC 当作微信/支付宝官方签名，它依赖你们商户网关先完成上述验证。主站再次核对金额、套餐订单、支付方式与币种，在 D1 事务中用唯一收据和 activation_id 幂等激活订阅，前端轮询权益状态。套餐 ¥99/14天、¥399/月、¥3990/年；有效试用转首张月付订单自动抵扣 ¥99，前端收银实付以订单返回为准。当前退款、月转年折算、对公到账人工后台、自动账单对账/关单尚未实现。到期不自动扣款。

#### 比赛期演示：个人收款码桥（payment-bridge）

`payment-bridge/` 是实现上述契约的演示商户网关：主站下单验签 → 收银页展示店主**个人收款码**（`payment-bridge/assets/wechat-qr.png` / `alipay-qr.png`）→ 付款人登记「我已转账」（仅登记，不激活）→ 店主在 `/admin` 人工核对实际到账后确认 → 桥向 `notify_url`（公开网关 `/webhooks/payment`）发送重新签名的统一事件 → 主站验签开通。没有「模拟成功即开通」的后门，开通仍由主站验签回调完成；主站代码零改动。部署与联调步骤见 `payment-bridge/README.md`。

演示与合规边界：这是比赛期方案，向评委须明确说明为「个人收款码 + 人工确认」，不冒充官方商户收单；个人收款码不能用于真实经营收款（人民银行 259 号文及平台规则），正式对外收费前必须换成微信支付商户 / 支付宝商家网关，届时只改 `PAYMENT_BRIDGE_URL` 指向。个人码没有支付回调，到账核对永远是人工动作，确认记录保留在桥的订单状态里。

### 生产扩量前的明确限制

- 审计保存在应用只追加的 D1 表，并非外部不可篡改日志服务；部署管理员有 DB 权限。
- 身份边界和账号注册复用 ChatGPT Sites，不是国内手机号登录；需要独立面向工厂公开销售时可迁移到自有认证与境内主站/境外网关。
- 工单模型预算采用调用前闸门，没有全并发原子预留；Token 费用只是估算，凭供应商账单核实。
- 日/周报使用模型分析真实记录；假设结果只形成建议，尚未自动更新假设状态、情报回写和自主度升降。
- 招标逐条响应、公开项目线索抓取、联网市场增量研究、退款和完整发票后台不在此次实现中。
- R2 原件、客户消息与审计当前不自动过期；正式收真实客户数据前应确定保留期、删除流程、隐私文本和本地业务资质。
